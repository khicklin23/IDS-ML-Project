Maps docs/PRODUCT_VISION.md delivery stages to Git-kb tasks. Foundation: tasks/environment-setup, tasks/synthetic-data, tasks/train-evaluate (all completed 2026-10-10). First complete experience: tasks/inference-replay, tasks/alert-store (score/replay and alert logic, kept separate per vision), then tasks/streamlit-ui as a thin end-to-end slice blocked by both. Expanded simulation (not yet task-ified, create when Stage 2 nears acceptance): additional scenario families beyond the first few, configurable experiment/architecture comparison with run records, incident correlation grouping alerts, report/dataset export, bounded larger-scale streaming generation with progress/cancellation. Advanced research (not yet task-ified, needs documented Stage 1-2 results first per vision): temporal/anomaly modeling, robustness across distribution shift as a standing evaluation suite. Rationale for not pre-creating Stage 3/4 tasks now: vision explicitly gates added complexity on documented need from earlier results, and premature fine-grained scoping would lock decisions (model size, storage, scenario count) the vision defers to implementation time. Revisit this note whenever stage boundaries move.

**Deployment pivot, 2026-10-10 (supersedes prior UI assumptions):** user's real end target is a static, single-dashboard precomputed site (deployable e.g. on Vercel), not the current interactive multipage Streamlit app -- that app is an explicitly disposable intermediate step. Also wants: IDS-analyst-style dataset display (source/dest IPs etc.), and large-batch precomputed runs (~50k rows mentioned) rather than live in-browser training. Immediate priority: `tasks/attack-type-classifier` -- real multiclass attack-type classification, NN-first (done, see below).

**Backend/UI handoff, 2026-10-10 (same day, later):** user explicitly paused UI work until backend is "completely set up" -- may hand UI to a separate agent. Built `src/ids_ml/report.py::build_report()`, the stable contract: one `report.json` per run (dataset stats + sample flows with new `src_ip`/`dst_ip` display fields + binary model-vs-rule metrics + multiclass per-class metrics/confusion matrix + sample alerts carrying both `scenario_ground_truth` and the model's own `predicted_scenario`). A real example is on disk at `data/generated/showcase/` (seed 1, 21k rows, verified full 6-class coverage -- binary F1 0.956 vs rule F1 0.443, multiclass macro-F1 0.94). `tasks/static-dashboard-ui` has the full contract spec for whoever builds the UI next; `tasks/backend-polish` tracks ongoing hardening (split-stratification bug below is top of that list) without blocking the UI task -- `report.json`'s shape should stay stable (bump `REPORT_VERSION` in `report.py` if it must change) even as numbers underneath improve.

**Model maturity, approved 2026-10-10 ("do em all") -- DONE, same day:** `tasks/model-maturity` completed. Schema v1.2.0 (`prior_gap_s` inter-arrival feature), `stealth_mode` on all 5 attack injectors, `src_ml/robustness.py` (ordinary distribution-shift + stealth-evasion eval), `src_ml/openset.py` (max-softmax unknown-attack rejection), calibration check wired into `report.json` (`REPORT_VERSION` 1.1.0, additive). Headline honest findings, all backed by real experiments not assumption: (1) a feature that helps the normal case (prior_gap_s) can *hurt* adversarial robustness on its own -- fixed by combining it with mixed normal+stealth training; (2) open-set rejection works for attacks with a distinctive instantaneous signature (port_scan: 40% novel-detection at threshold 0.95) and doesn't for purely temporal ones (beaconing: ~0% at any threshold, confirmed via two different methods) -- real evidence for `tasks/temporal-modeling`, not a guess; (3) the model is measurably overconfident, same root cause behind both the open-set and calibration findings. Showcase bundles regenerated under the new schema: 21k-row bundle (binary F1 0.937 vs rule 0.357, multiclass macro-F1 0.945) and 50k-row bundle (binary F1 0.991 vs rule 0.324, multiclass macro-F1 0.994, ECE 0.003). `tasks/temporal-modeling` (draft, blocked_by model-maturity, now unblocked) is the bigger follow-on tier -- sequence-aware modeling per session instead of per-flow, now with concrete empirical motivation from the open-set beaconing result, added as a comparison tier alongside the existing MLP, not a replacement.

**Model version registry, 2026-10-11 (user-directed), v1-v4 -- DONE:** user wants the classifier explicitly versioned rather than overwritten, so improvement over time is a measured comparison, not a claim. `tasks/model-versions` built `src_ml/versions.py` + `models/sequence.py`/`models/sessions.py` (the GRU work, superseding `tasks/temporal-modeling`'s original scope). v1 = per-flow MLP, normal-only. v2 = same architecture, normal+stealth mixed training. v3 = session-level GRU, normal-only (isolates architecture-alone effect). User then looked at the UI numbers, asked why v3 lagged v2 and whether beaconing was still broken, and asked for a v4 that combines both fixes plus more data. Investigation found a real bug, not just a missing feature: `max_seq_len` was a hardcoded guess (50) instead of computed from real data -- normal-mode sessions routinely run 100-250 flows, so v3 was only ever seeing a truncated fraction of exactly the hardest-to-distinguish sessions (benign vs. beaconing). Fixed (now auto-sized from the data), which also corrects v3's own numbers, not just unlocks v4. v4 = GRU + mixed training + the fix + ~2x the dataset. Result: v4 matches v2 at a perfect 1.0 stealth macro-F1, **per-class**, including beaconing (not just the aggregate) -- confirmed by checking precision/recall per class, since an aggregate number alone would have hidden exactly the failure mode being chased. Honest scope note carried into the task doc: this is near-perfect on held-out sessions from the *same* generation distribution, not the harder distribution-shift bar in `tests/test_robustness.py` (separate, already-passing test, not rerun here).

**Known bug surfaced building the showcase bundle:** `split_dataset` groups by session without label stratification -- roughly half of seeds tried at showcase scale landed zero val/test rows for at least one class. This is the same failure mode that broke the Streamlit UI's default config earlier (see tasks/streamlit-ui), now hit twice more at larger scale. Worked around by seed search each time so far; a real fix (stratified grouped split) is `tasks/backend-polish` item 1 and matters for `tasks/static-dashboard-ui` too (document in that task before using a new seed for any user-facing demo).

**Parallel work split, 2026-10-10:** tasks/streamlit-ui (agent-2-env-setup) and tasks/scenario-library (new, for a second agent) are running concurrently by design -- UI consumes the data/model/alert modules as a stable read-only surface; scenario-library only adds to scenarios.py/schema.py/generator.py additively. See each task doc's "Coordination boundary" section for the exact file-scope split and shared-file etiquette.

**User priority, 2026-10-10 (applies starting now, not just at Stage 3):** the model is the intended primary attack-identifier, not rule code. Any rule-based baseline built in tasks/inference-replay stays strictly a comparison signal (per vision's "rule/model comparison" workspace) and must never become the path that actually decides severity or attack type in tasks/alert-store. The user also wants synthetic data fidelity (packet/byte/timing realism) to keep improving, and wants the classifier upgraded from binary normal/suspicious to multiclass scenario-family prediction sooner rather than later -- this reorders Stage 3's "multiclass scenario recognition" item ahead of other Stage 3 candidates once the Stage 2 vertical slice lands. Comparison metrics (model vs. rule baseline) should be computed and surfaced wherever both exist, so the model's superiority is demonstrated, not assumed.
