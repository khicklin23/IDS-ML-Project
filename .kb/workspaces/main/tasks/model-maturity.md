User explicitly approved all suggested maturity improvements 2026-10-10 ('do em all'), ordered by value/complexity in the original suggestion. Supersedes backend-polish item 4 (dataset realism beyond IPs). Scope, in build order:

1. Distribution-shift robustness eval: evaluate the trained multiclass model on flows generated from a DIFFERENT seed/config than it trained on (not just a held-out split of the SAME generation run). Proves the model learned general attack signatures, not synthetic-generator quirks. Vision explicitly calls this out ('performance across unseen scenarios and changed traffic distributions').
2. Noisier/adversarial scenario variants: add a stealth/noise knob to existing scenario injectors (slower port scans, larger beaconing jitter, etc.) so attacks are harder to distinguish from benign traffic -- tests whether the model generalizes or just memorizes clean synthetic signatures. Combine with item 1: evaluate the clean-trained model against noisy variants too.
3. Open-set / unknown-attack detection: the multiclass model currently always picks one of the trained classes, even for something it's never seen -- a real IDS's hardest job is flagging 'this doesn't match anything known.' Add a confidence-threshold-based unknown/novel rejection path (standard max-softmax-probability baseline for open-set recognition). Validate by holding one attack family entirely out of training and confirming those flows get flagged as low-confidence/unknown rather than confidently mislabeled as a known class. This is the single highest-value item: a thing rule-based code structurally cannot do, directly serving the project's core 'real use case for the neural network' requirement.
4. Additional realistic flow fields: TCP-flag-style outcome detail and/or bytes/packets-per-second rate features, pushing further toward real NetFlow/IDS telemetry shape (CICIDS/NSL-KDD-ish) without inventing ad-hoc schema.
5. Confidence calibration check: verify the multiclass softmax probabilities are roughly trustworthy (e.g. expected calibration error / reliability check), not just accurate on average.

- `test_model_generalizes_to_an_ordinary_distribution_shift`: trained-on-one-config model evaluated on a *differently shaped* config (different seed, host count, traffic rate, episode mix) -- macro_f1 > 0.7, confirming it learned attack signatures, not generator quirks.
- `test_stealth_variants_expose_a_real_weakness_that_mixed_training_fixes`: the full honest finding (see schema note below) -- baseline (normal-only training) macro_f1 drops >0.25 on stealth variants; mixing stealth examples into training recovers most of it (>0.15 improvement) without regressing normal-case performance (still >0.85).
- **Real finding worth highlighting**: the first fix attempt (just add the new `prior_gap_s` feature, item 4) actually *worsened* stealth-robustness on its own (0.831 -> 0.645 macro_f1) even though it substantially improved normal-case beaconing precision (0.448 -> 0.708) -- because inter-arrival gap is *exactly* what an attacker pacing an attack slower would be changing, so a feature that's very informative on the training distribution can make the model more brittle to evasion. Combining the new feature WITH mixed stealth/normal training recovered robustness (stealth macro_f1 back to ~0.83) while keeping the precision gain. This is now the main documented result for item 2 -- a genuine security-ML lesson, not something to gloss over.

**Item 4 (partial) done**: added `prior_gap_s` (seconds since the previous flow in the same session; standard NetFlow-derivable inter-arrival feature) to `FEATURE_COLUMNS` -- schema bumped to v1.2.0. This is beaconing's actual discriminating signal (regular intervals), which no single-flow feature previously captured. TCP-flag-style detail and rate features not yet added.

**Item 3 (open-set detection) done** (`src/ids_ml/openset.py`, `tests/test_openset.py`): `classify_with_rejection` + `evaluate_open_set`, max-softmax-probability thresholding (the standard baseline method). Full, honest, three-part finding from real experimentation:
- Holding `outbound_transfer` out of training: **never** flagged unknown, any threshold up to 0.99. It's deliberately feature-ambiguous with benign large uploads by design (see that scenario's own docstring) -- not an overconfidence bug, the per-flow features genuinely don't disambiguate it.
- Holding `beaconing` out: **also** never meaningfully flagged (max ~1.4% detection at threshold 0.99, where false-rejection of known classes already balloons to 7.8%). Tried a second, different detection method too (feature-space nearest-centroid distance) -- same result: beaconing's min-centroid-distance is well within the normal in-class distance range. Root cause confirmed two ways: beaconing's actual signal (regularity *across* flows over time) isn't expressible in any single flow's features, however augmented -- this is real evidence for `tasks/temporal-modeling`, not a guess.
- Holding `port_scan` out instead (a class with a genuinely distinctive *instantaneous* signature: tiny packets, rejected/timeout, random ports): **works well** -- at threshold=0.9, 31% novel-detection / 14% false-rejection / 76.5% known-accuracy; at 0.95, 40% novel-detection. Confirmed the real tradeoff curve (higher threshold = more novel detection, more false rejection, both move together as expected).
- **Conclusion shipped as the honest capability**: open-set rejection via confidence thresholding genuinely works for attacks with a distinctive per-flow footprint, and doesn't for purely temporal/behavioral ones -- both outcomes are documented, not just the success.

**Item 4 (partial, by design)**: added `prior_gap_s` (schema v1.2.0) -- the main realism win, see item 1/2 finding above for why it's a double-edged feature. TCP-flag-style detail / rate features not added -- judged lower value than items 1/2/3/5 given the time budget; noted as open future work, not silently dropped.
